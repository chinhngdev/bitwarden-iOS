## Projects

Two apps share this repo:
- **Bitwarden Password Manager** — `Bitwarden.xcworkspace` / `project-pm.yml`
- **Bitwarden Authenticator** — `project-bwa.yml`

Extensions (ActionExtension, AutoFillExtension, NotificationExtension, ShareExtension, WatchApp) are part of the Password Manager target.

## Setup

Requires: Xcode 26.2 (see `.xcode-version`), Ruby 3.4.2 (see `.ruby-version`), `mint`, `brew`.

```bash
brew bundle
./Scripts/bootstrap.sh   # installs Mint tools, runs XcodeGen for all projects, sets up git hooks
```

XcodeGen regenerates `.xcodeproj` files from `project-*.yml` — never edit `.xcodeproj` directly.

Mocks are generated by Sourcery: `./Scripts/generate-mocks.sh`

## Build & Test

Build for simulator:
```bash
./Scripts/build.sh project-pm.yml Bitwarden Simulator
./Scripts/build.sh project-bwa.yml Authenticator Simulator
```

Run all tests (via Xcode or fastlane). Run a single test plan:
```bash
xcodebuild test -workspace Bitwarden.xcworkspace -scheme Bitwarden \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -testPlan <PlanName>
```

Run a single test class:
```bash
xcodebuild test -workspace Bitwarden.xcworkspace -scheme Bitwarden \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -only-testing:BitwardenSharedTests/ClassName
```

## Architecture

All feature code lives in `BitwardenShared/` (Password Manager) or `AuthenticatorShared/` (Authenticator). Each is divided into `Core/` and `UI/`, each further subdivided into exactly these domains: `Auth`, `Autofill`, `Billing`, `Platform`, `Tools`, `Vault`. Do not add new top-level subdirectories under `Core/` or `UI/`.

### Core Layer

- **Models** — `Domain/`, `Enum/`, `Request/`, `Response/` subdirectories
- **Data Stores** — CoreData, Keychain, UserDefaults persistence
- **Services** — business logic, SDK interaction, networking via `Networking/` package
- **Repositories** — aggregate services; expose data ready for the UI

Services and repositories are always defined as protocols with mock implementations (generated by Sourcery with `AutoMockable`) so the UI layer can be tested in isolation.

### UI Layer (Unidirectional Data Flow)

Each feature follows this pattern:

```
Coordinator → Processor ↔ State → View
```

- **Coordinator** — manages navigation within a container (UINavigationController, UITabBarController). Creates processors/views, delegates business logic decisions to a **Router** when needed.
- **Processor** — owns `State`, handles `Action` (sync, from user gestures) and `Effect` (async, side-effects). Requests navigation via coordinator. The only place state mutation happens.
- **State** — plain struct with all data needed to render a view.
- **View** — renders state via a `Store`. Sends actions/effects to the processor; never mutates state directly.
- **Actions / Effects** — enumerations. Adding a case forces the compiler to require handling in the processor.
- **DefaultAppModule** — single entry point that wires all coordinators; injected service container flows through here.

### Test Architecture

- **XCTest** (existing files): inherit from `BitwardenTestCase`, `setUp()` creates fresh instances, `tearDown()` nils them out.
- **Swift Testing** (new files): `struct` with `init()` for setup, `@Test` attribute, `#expect()` / `#require()` assertions.
- Test naming: `test_<functionName>_<behaviorDescription>` (XCTest) / `<functionName>_<behaviorDescription>` (Swift Testing).
- Test ordering: group by function name alphabetically; within a group, order logically (success → failure → edge cases).
- Views are tested with **ViewInspector** (interactions) and **Snapshots** (light/dark/accessibility modes).
- Test files are co-located with the source they test.
